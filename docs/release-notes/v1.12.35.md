# v1.12.35

传输层语义与 keepalive 参数的补丁版。`v1.12.34` 之后 `transport` 层的失败语义又收敛了一轮：写不出去的帧报可重试的 `Unavailable`，等不到响应一律报不可重试的 `Canceled`，`Close()` 不再代替在途调用取消自己；本版在此之上把批处理 flush 的写 deadline、keepalive 与读超时对齐 gRPC 的标准取值。对外 API 签名没有变化。

## 本次修复（`c837e5b..229c170`）

| 位置                                   | 处理                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `transport/channel.go` `newChannel` 的 flush timer | 写之前用 `writeTimeout` 自装 deadline，不再沿用上一次 `Send` 留下的旧值：两次写间隔超过 3s 时，那批帧不会因为过期 deadline 立刻写超时                                   |
| `transport/driver.go`                | `defaultKeepalive` 从 `3*defaultTimeout`（9s）改为固定的 10s，落在 gRPC 对客户端 keepalive 的下限上；`defaultReadTimeout` 随之是 `3*defaultKeepalive` = 30s，空闲连接在放弃前能收到两次 ping |
| 注释与测试                                | `Send` 两条路径都装 deadline 且失败包 `Unavailable`；`WithReadTimeout` 的 3\*keepalive；服务端 payload 读共享 header 的 deadline；根包 `Close` 的 27s → 30s；`options_test` 的 `Keepalive()` 断言 9s → 10s |

## 行为变化

- keepalive 间隔 9s → 10s，客户端读超时 18s → 30s（`transport.WithReadTimeout` 可覆盖）。空闲连接被判定失联的时间从 18s 推迟到 30s。
- 批处理（`WithBufSize > 0`）时，flush 用的写 deadline 每次自己装，不再继承上一次 `Send`。
- 客户端写失败（`SetWriteDeadline` 或 `WriteTo`）报 `Unavailable`：帧没写完，对端不会执行，调用可重试。等响应失败（含自己的流超时）报 `Canceled`：对端是否执行未知，不重试。
- `Close()` 与 `cc.Close()` 不再唤醒在途调用，它们照旧在自己的流超时上结束；只有连接自己断了，在途调用才会立刻报 `Canceled`。
