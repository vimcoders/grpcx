# v1.12.42

修 P1-1：ping 的预算不再等于 ping 的间隔。此前 `defaultKeepalive = defaultTimeout` 把两个时间焊在同一根数上，`Ping` 无论取哪个访问器都只能拿到「间隔」本身，一次 ping 撑满整个周期后，下一个已经启动。这一版把 `defaultKeepalive` 解绑为 `3 * defaultTimeout`，并让 `Ping` 跑在 `min(Timeout(), Keepalive())` 上。

## 改动

| 位置 | 处理 |
| --- | --- |
| `transport/driver.go` `defaultTimeout` | 3s → 1s |
| `transport/driver.go` `defaultKeepalive` | `defaultTimeout` → `3 * defaultTimeout`（3s），与 ping 预算解绑 |
| `transport/client.go` `Ping` | 新增子 context，预算 `min(c.Timeout(), c.Keepalive())`，注释重写 |
| `transport/client.go` `createStream` | caller deadline 近于 readTimeout 时取小值：`min(cmp.Or(time.Until(dl), timeout), timeout)`，注释同步 |
| `transport/client.go` `WithTimeout`、`Timeout()` | 注释补上 `Ping` 这一个消费者，并写明受 `Keepalive()` 上限约束 |
| `transport/driver.go` 两个常量注释 | 重写为「预算必须在间隔内失败」的推导，取代原先「两者相等」的说法 |

派生值：`defaultReadTimeout = 3 * defaultKeepalive` 仍是 9s；`defaultWriteTimeout = defaultTimeout` 由 3s 降到 1s。

## 行为变化

- **ping 预算 1s、间隔 3s**：一个 ping 一定在下一个 ticker 触发前失败，同一条连接上不会再压两个 ping；`balancer` 那轮串行 ping 也不会被单个静默后端拖成 N×1s。
- **`Options.Timeout()` 默认 3s → 1s**：服务端 `defaultMethodHandler` 的 handler 上限随之从 3s 收到 1s，写超时同样是 1s。这次收口是刻意的——ping 是一次真实调用，客户端等它的时间要与服务端处理它的预算同源，否则会出现客户端已放弃、服务端还在跑同一个 ping。
- **`min` 是上限，不是第二套预算**：`WithTimeout` 调到 3s 以上会被 `Keepalive()` 截回 3s；默认值下它不生效。
- **读超时不变**：仍是 9s，空闲连接可容纳两次 ping 才被判死。

## 测试

- 新增 `TestPingEndsAtItsOwnBudget`：`WithTimeout(50ms)` 配 `WithReadTimeout(1s)`，用不响应的 `answeringSender` 实测 `Ping` 耗时，连跑三次稳定在 0.05s，证明它读的是自己的预算而不是 1s 读超时。
- 新增 `TestKeepaliveOutlastsThePingBudget`：钉住 `defaultKeepalive > defaultTimeout` 和 `defaultReadTimeout > defaultKeepalive`，把常量改回相等会立刻红。
- 新增三条 `createStream` deadline 用例：caller 更近时取 caller、caller 更远时不放大、caller 已过期则流出生即弃。
- `TestOptionsAccessors`、`TestDefaultOptionsCarryEveryPackageDefault`、`TestDefaultMethodHandlerCapsTheHandlerDeadline` 中的字面 `3s` 全部改为引用 `defaultTimeout`，断言跟随常量而不是跟随某个版本的数字。
- 门禁全绿：`gofmt -l .` 空、`go vet ./...` 空、`golangci-lint run` 0 issues、`go test ./... -count=1` **158 通过 0 失败**（Windows，`CGO_ENABLED=0`）；`transport` 包 `-count=5` 亦全过。
