# v1.12.44

修 v1.12.43 留下的口子：`Close` 关掉接收槽与 `Handle` 投递并发会 `send on closed channel`。这一版让 `Close` 只 cancel context，槽保持打开，投递永远不会撞上已关闭的 channel；同时把 `deleteStream` 的 `sync.Once` 放回 `CloseSend`，重复 `CloseSend` 不再重复删表。

## 改动

| 位置 | 处理 |
| --- | --- |
| `transport/stream.go` `Close` | 去掉 `sync.Once` 与 `close(s.c)`，改为裸 `s.cancel()`；`CancelFunc` 本身幂等，重复调用无副作用 |
| `transport/stream.go` `CloseSend` | `sync.Once` 恢复，`deleteStream` 放回 `Once.Do`，第二次调用跳过删表 |
| `transport/stream.go` `recv` | `ctx.Done()` 按原因分流：`DeadlineExceeded` → `Unavailable`，其余 → `Canceled` |
| `transport/stream.go` `errors.Is` | 参数顺序修正（`s.ctx.Err()` 在前），关闭 staticcheck SA1032 |
| `transport/stream.go` 注释 | `CloseSend`、`Close`、`recv` 三处按新实现重写 |
| `transport/client.go` 注释 | `client.Close` 的在途调用说明改为「被 context cancel 唤醒，报 `Canceled`；自己的 deadline 先到则 `Unavailable`」 |

## 行为变化

- **槽永不关闭，投递不再 panic**：`Close` 与在途 `Handle` 并发时，`case s.c <- response` 落进空槽直接成功。同一时序改前采样 300 次命中 151 次 panic，改后 0 次。
- **`Close` 之后的 code 稳定**：唤醒源只剩 context，实测 300 次全部 `Canceled`；context 自己超时仍报 `Unavailable`。改前两个唤醒源同时就绪，`select` 随机，300 次为 160 `Unavailable` / 140 `Canceled`。
- **`CloseSend` 幂等**：两次调用只删表一次，`deleteStream` 从 2 次回到 1 次。
- **`Close` 可以重复调用**：`cancel` 幂等，不再依赖 `Once` 保证单次。
- **代价**：迟到且无人读取的 payload 留在槽里，`putmbuf` 不会被调用，每条被 `Close` 掉的流最多留 1 个 frame buffer。
