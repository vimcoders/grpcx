# v1.12.46

`Handle` 交接前先看流上下文：调用已经结束的，payload 直接还池，不再塞进一个没人读的槽。这一版不改结构、不加锁，只把「关闭之后到达」这条常态路径的残留清零。

## 改动

| 位置 | 处理 |
| --- | --- |
| `transport/stream.go` `Handle` | 在 `select` 之前插入 `if s.ctx.Err() != nil`：已结束则 `putmbuf(p)` 并 `s.Close()`，不投递 |
| `transport/stream.go` `Handle` 注释 | 重写：已结束的调用把 payload 还池，而不是停在没有读者的槽里；槽已占用同样还池 |
| `transport/stream_test.go` | `TestClientStreamCloseLeavesTheSlotOpenForLateReplies` → `TestClientStreamCloseDropsLateReplies`，新增 `len(s.c) != 0` 断言，要求槽内不留回复 |

业务代码净改动 4 行，位于 `Handle` 的 `response` 构造之后、`select` 之前。`Close`、`CloseSend`、`recv` 与 `client.go` 均未改动。

## 行为变化

- **`Close` 之后到达的回复一律还池**：`s.ctx.Err()` 非 nil 时直接 `putmbuf` 并收尾，槽保持空。这条覆盖 `Close`、调用方取消、自身 deadline 三种结束方式。
- **交接仍不看参数 `ctx`**：`client.Handle` 传入的是 `context.WithoutCancel`，永远不 err；判断依据仍是流上下文。
- **`default` 分支依旧是兜底**：槽已满时归还，正常路径（每流一次投递）不触发。

## 已知取舍

**P1-6 的残留窗口从「必然」收窄为「交错」**。`Handle` 的判空与投递之间没有同步：`s.ctx.Err()` 读回 `nil` 之后、`s.c <- response` 之前若恰好结束，投递仍会成功，payload 留在槽里。

- 最坏情形实测：`Handle` 与 `Close` 同起点竞速 30000 次，660 次槽内留回复（约 2.2%）。这是交错密度最高的构造，真实链路的 `Handle` 先阻塞在 `Recv`、`Close` 从调用方线程进入，低于该值。
- 后果是这 1 个 frame buffer 少还一次，随 `clientStream` 一起被 GC。不是增长型泄漏。
- 要彻底闭合必须把判空与投递放进同一临界区（`slot sync.Mutex` + `dead bool`），本版选择不加锁。
