# v1.12.48

P2-1 收口。`RoundTrip` 从"传对象、回对象"改成"传字节、回字节"：调用方寄出的 payload 原样上线，reply 以 `mem.Buffer` 交回来、由调用方自己 `Free`。归还的入口第一次伸到了包外。

## 改动

| 位置 | 处理 |
| --- | --- |
| `transport/driver.go` `RoundTripper` | `RoundTrip(ctx, req *api.Request) (*api.Response, error)` → `RoundTrip(ctx, p []byte, opts ...CallOption) (mem.Buffer, error)`，`driver.go` 不再 import `generated/api` |
| `transport/client.go` `RoundTrip` | 头由 `opts` 现拼，`ctx` 的 deadline 覆盖 `Timeout`，`StreamID` 最后写；状态非 OK 直接返回 `status.Error`，不碰 Buffer |
| `client.go` 根包 | `ClientConnInterface.RoundTrip` 同步改签名；选路不再携带方法名 |
| `transport/stream.go` | 请求头的 `Code`/`Desc` 初始化删掉：零值就是 `codes.OK`，且无人回读 |
| `transport/channel.go` | 变量 `payload` 改名 `p`，与帧长变量 `h` 对齐 |
| 调用点与测试 | 全部按新签名重写 |

## 为什么不是"加一个归还函数"

`*api.Response.Payload` 的内存来自 `mem.DefaultBufferPool()`，而 `putmbuf` 是 `transport` 包内私有 —— 外部拿到 reply 之后没有任何出口把这块内存还回去，只能等 GC。补一个导出的归还函数是最小改动，但它把"这块内存谁拥有"推给调用方去猜：一个 `*api.Response` 里既有要归还的字段，也有不要的。

返回 `mem.Buffer` 把所有权写成显式的：谁拿到谁 `Free`，没有第二种解释。

## 归还的实际边界

`mem.NewBuffer` 只在容量够到池的 tier 时才入库。实测 `DefaultBufferPool()`：

| 载荷 | 池给的容量 | 动态类型 | `Free` |
| --- | --- | --- | --- |
| 200 B | 256 | `mem.SliceBuffer` | 空操作 |
| 1024 B | 4096 | `*mem.buffer` | 归还 |
| 2048 B | 4096 | `*mem.buffer` | 归还 |
| 5000 B | 16384 | `*mem.buffer` | 归还 |

分界点是 256 字节：池的最小 tier 就是 256，往上一档直接 4 KB，越过 1 KB 的池化阈值。因此 ≤ 256 B 的 reply 本来就不进池，`Free` 是空操作 —— 不是漏了归还，是无池可还。两条分支各有测试守着（`TestRoundTripHandsBackAPooledBuffer` / `TestRoundTripSmallReplyFreesAsANoop`）。

## 三个语义约定

- **失败不带 Buffer**：对端的错误路径统一回 `api.Empty`，序列化后 0 字节，线上是零长帧，客户端读到的 `resp.Payload` 是 `nil`。所以非 OK 分支只有 status，没有需要归还的东西。
- **入参归还即可复用**：`RoundTrip` 返回后，传进去的 `p` 可以立刻改写。
- **选路不看方法名**：后端由 K8s Service / DNS 给出，池内每个 endpoint 等价，方法名只作为帧内容走线。
