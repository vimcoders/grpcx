# v1.12.52

帧层去掉 protobuf：请求与回包不再被包进 `api.Request` / `api.Response`，请求头直接是 `CallOptions`，回包直接是 `Buffer`。

## 改动

| 位置 | 处理 |
| --- | --- |
| `generated/proto/api.proto` | 删 `Length` / `Authority` / `Closed` 三字段，`StreamID` 移到 7 号位；删 `message Request` 与 `message Response` |
| `generated/api/api.pb.go` | 随 proto 重生成，少 164 行 |
| `transport/driver.go` | `RoundTripper.RoundTrip` 与 `Recver.Recv` 改用 `Buffer`，删 `google.golang.org/grpc/mem` import；文件末尾新增 `type Buffer interface { Free(); ReadOnlyData() []byte }` |
| `transport/channel.go` | 新增 `defaultBuffer []byte`（`Free` 回池、`ReadOnlyData` 返回自身）；`Recv() (Buffer, error)` |
| `transport/stream.go` | 新增 `reply{ CallOption; Buffer }`；`clientStream.c` 由 `chan *api.Response` 改为 `chan *reply`；`RecvMsg` 先 `Free` 再 `Unmarshal`；`apply` / `WithCallOptions` 同步收窄 |
| `transport/client.go` | `Invoke` 只留编解码，其余走 `RoundTrip`；`RoundTrip` 返回值改 `Buffer` |
| `client.go` | 新增 `type Buffer = transport.Buffer`，`ClientConnInterface.RoundTrip` 与 `client.RoundTrip` 同步 |

## 为什么改

`api.Response` 当初是 `Options` 加一段 `Payload` 字节，`api.Request` 同理。传输层真正握在手里的就是「一个头 + 一段字节」；包一层 protobuf 只为把两者绑在一起传出来，代价是每次回包都要多解剖一次。

现在这层壳拆了：回包是 `reply{CallOption; Buffer}`，`Buffer` 就是那段字节本身，`ReadOnlyData()` 直接交给 `Unmarshal`。帧格式没变（仍是头帧加数据帧两帧），变的是两者在 Go 里怎么被握在手里。

## 破坏性变更

- `ClientConnInterface.RoundTrip` / `client.RoundTrip` / `transport.RoundTripper.RoundTrip` 的返回类型由 `mem.Buffer` 改为 `grpcx.Buffer`（`Buffer = transport.Buffer`）。外部实现 `RoundTripper` 的需要同步签名，不再依赖 `google.golang.org/grpc/mem`。
- `api.Request` / `api.Response` 已删除；`api.CallOptions` 去掉 `Length` / `Authority` / `Closed`，`StreamID` 编号从 5 变为 7。
- `Recv` 对零长帧不再返回 `nil`，返回一个空的 `Buffer`，对其调用 `Free()` 不做任何事。

## 顺带修掉的两处

1. **`StreamID` 会被调用方覆盖。** 原来 `in := api.CallOptions{StreamID: s.id}` 之后才 `o.apply(&in)`，而 `apply` 里是 `cmp.Or(c.StreamID, opts.StreamID)`，调用方传一个非零 `StreamID` 就能把帧路由到别的流，结果是 `Unavailable`。现在 `in.StreamID = s.id` 放在所有 option 之后，由本 transport 分配的 id 说了算；`TestRoundTripOwnsTheStreamID` 锁住这条，把顺序改回去该用例立刻失败。
2. **失败调用泄漏回包 buffer。** `RoundTrip` 的非 OK 分支原来直接 `return nil, status.Error(...)`，把 `reply.Buffer` 丢在池外。现在先 `reply.Free()` 再返回；`TestRoundTripFreesTheBufferOfAFailedCall` 用 `countingBuffer` 断言恰好 Free 一次。

## 已知取舍

**`defaultBuffer` 没有引用计数。** 它是裸 `[]byte`，`Free()` 直接把切片交回池；Free 两次会把同一块内存交还两次，之后两个持有者可能拿到同一段字节。当前契约是「一个持有者，恰好 Free 一次」，写在 `Buffer` 的注释里，没有运行时防护。要走引用计数得把它变成指针类型并连带改 `getmbuf` 的返回，本轮没做。

沿用 v1.12.46：**P1-6**（`Handle` 判空与投递之间的交错窗口）按已知取舍处理，最坏构造实测约 2.2%，后果是 1 个 frame buffer 少还一次、随流被 GC，不是增长型泄漏。
