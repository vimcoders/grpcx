# v1.12.56

`Codec` 的选择收口到 `Options.newCodec`，并把「开/关批量发送」的取舍实测清楚。

## 改动

| commit | 范围 | 内容 |
| --- | --- | --- |
| `f11174c` | 13 个文件，194+/81- | Codec 由 `Options.newCodec` 统一派生，`codec` 更名 `emptyCodec`，对齐注释与测试 |

`client` 与 `server` 原来各自构造 Codec，现在都从同一个方法取：

```go
func (o Options) newCodec() Codec {
	if o.bufsize > 0 {
		return emptyCodec{o.ecodec}
	}
	return defaultCodec{o.ecodec}
}
```

阈值是唯一的开关。`bufsize > 0` 时装 `emptyCodec`，`proto.Message` 也交给
`encoding.Codec`，产出的 bytes 不归池所有；否则装 `defaultCodec`，
`proto.Size` 定容后 `MarshalAppend` 进池 buffer。

顺带修掉一处与实际相反的注释：根包 `WithCodec` 原写「A nil codec is ignored」，
但 `transport.WithCodec` 没有 nil 检查，会原样存进去。

## 批量发送的取舍

### 实测数据

环境：i5-14600KF，`GOMAXPROCS=20`，Windows 11，TCP loopback，本地 Echo 服务，
`bufSize = GOMAXPROCS*1024`，`benchtime=2s`，3 轮取中位数。

| 报文 | 关批量 | 开批量 | 差距 |
| --- | --- | --- | --- |
| 1K | 14.70 µs/op | 12.15 µs/op | 快 17%，1.21x |
| 5K | 19.27 µs/op | 16.84 µs/op | 快 13%，1.14x |
| 1024K | 1.206 ms/op | 1.265 ms/op | 打平，差异在噪声内 |

分配次数两种模式基本相同（1K 75 → 74 allocs/op，5K 与 1024K 都是 75 和 78）。

1MB 那一行没有意义上的差异：单帧 1MB 远超 16KB 的批量阈值，`Send` 每次都直接
`WriteTo`，开不开走的是同一条路径。

### 开批量（`bufsize > 0`）

好处：

- `net.Buffers` 加 `WriteTo` 把多帧合并成一次 `writev`，小报文高并发下省掉大量
  syscall。1K 与 5K 的 13%~17% 就来自这里。
- 并发越高收益越明显，因为一次 flush 能合并更多帧。

代价：

- 帧最多在 `ch.bw` 里等一个 flush 周期（`defaultFlushInterval`，1ms）才上线，
  尾延迟有一个毫秒级的台阶。
- buffer 所有权转移：`Send` 返回后那些字节归 channel 管，调用方不得改动，也不得
  释放。这条约束从 `Sender` 一直传到 `RoundTrip` 的调用方。
- 为满足上面的约束，必须放弃池化。`emptyCodec` 让每个请求都走
  `encoding.Codec` 重新分配，1MB 场景的内存分配回到标准库水平。
- 错误路径留了一个窄窗口：`recv` 因超时或取消返回错误时，`defer Free()` 会把还
  挂在 pending batch 里的 buffer 归还池，下一次 `getmbuf` 复用同一片就会改写未
  flush 的帧。成功路径不受影响（`recv` 返回即意味着帧已发出）。

### 关批量（默认，`bufsize == 0`）

好处：

- `Send` 返回时字节已经在连接上，没有排队，也没有那 1ms 的台阶。
- `proto.Message` 走 `getmbuf(proto.Size)` 加
  `MarshalOptions{UseCachedSize: true}` 的 `MarshalAppend`，复用池里的 buffer，
  不额外分配。
- 所有权简单：`Send` 返回后调用方就能 `Free`，不需要 channel 替你保管。

代价：

- 每帧一次 write syscall。小报文高并发时 syscall 占比高，这正是 1K 少掉的那
  17%。

## 建议

- 默认保持关闭。延迟可预测、内存可池化，是多数服务端调用想要的样子。
- 小报文（≤5K）且并发高时打开，能拿到 13%~17% 的吞吐提升。
- 大报文（≥1MB）不必打开：批量不生效，还要付放弃池化的代价。

## 测试

- `TestNewCodecPicksByThreshold`：阈值 0 / 1 / -1 三档分别断言取到
  `defaultCodec` 或 `emptyCodec`。
- `TestDialContextChoosesTheCodec`：真实 TCP 拨号，断言客户端在
  `WithBufSize(1)` 下装的是 `emptyCodec`。这条行为是本次重构引入的，之前没有
  任何覆盖。
- 变异验证：把 `newCodec` 的 `o.bufsize > 0` 改成 `>= 0`，上面两个测试同时失败，
  确认它们真的守住了 0 这个边界。
